## 核心原则

- 先理解用户需求。只有用户说“跟进”后，才可以开始改代码。



## 注意

- 有不清楚的请使用联网工具或者让用户去帮你搜索，一定要保证信息主流不过时。
- 回答问题时避免过分的夸赞。请记住，你的回答不一定是对的，我的判断也不一定是对的。对待所有问题都要反复推敲或者必要的网络联网搜索验证，优先保证准确性，避免单一依靠于某个文件或者某个信息。必要时你可以主动向我索要补充信息或证据，回答时保持结构化输出，条理清晰。
- 先确认当前项目的实际情况在回答用户问题，避免凭借印象瞎猜。
- 如需启动服务，使用临时端口，结束后只关闭自己启动的服务，并确认端口已释放。
- 写文档的时候保持客观简洁清爽，规则只保留简洁清爽、通用、可执行的约定，具体细节按需查询，避免硬编码和过度展开。
- 视觉方面的判断交给用户来。

- 遵循 2026 年主流技术栈。
- 不硬编码。
- 不重复手动造轮子。
- 注释使用英文并保持客观清爽。
- 在 bug 修复后，先查 git log 和 git status，确认之前的改动是否已提交，提供 commit message（一句英文客观清爽，形式是：`<type>(<scope>): <description>`，scope 必填）给用户。避免用 with、`and` 等连接词追加次要改动或常规步骤。将提交信息单独放在一个 `text` 代码块中。
