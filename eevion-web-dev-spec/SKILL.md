## 核心原则
!!!先理解用户需求, 不要改代码, 只有用户说"跟进"的时候, 你才可以开始改代码

## 注意:

- 有不清楚的请使用联网工具或者让用户去帮你搜索, 一定要保证信息主流不过时.
- 回答问题时避免过分的夸赞。请记住，你的回答不一定是对的，我的判断也不一定是对的。对待所有问题都要反复推敲或者必要的网络联网搜索验证，优先保证准确性，避免单一依靠于某个文件或者某个信息, 必要时你可以主动向我索要补充信息或证据，回答时保持结构化输出，条理清晰。
- 先确认当前项目的实际情况在回答用户问题, 避免凭借印象瞎猜.
- 写文档的时候保持客观清爽, 规则只保留简洁清爽、通用、可执行的约定，具体细节按需查询，避免硬编码和过度展开。
- 视觉方面的判断交给用户来.

- 遵循 2026 年主流技术栈
- 不硬编码.
- 不重复手动造轮子.
- 注释保持客观清爽.
- 在bug修复后, 先查 git log 和 git status，确认之前的改动是否已提交, 提供commit message(一句英文客观清爽, 形式是:  <type>(<scope>): <description>，scope 必填)给用户. 避免用 with、`and` 等连接词追加次要改动或常规步骤。将提交信息单独放在一个 `text` 代码块中

## 补充
- 注释默认不写；仅当遗漏会误导后续修改时，用一两句英文 TSDoc 说明设计意图（Why）与约束。Why 内联说完整，引用决策文档只用完整路径且删除后注释仍成立。魔数优先转为具名常量，注释只写取值依据。约束优先由类型、lint 或测试承载：不引序号、不复制他处数值、不写"保持同步"类许诺；无法执法的软关系用软词表达。换行服务于语义结构而非字符长度。
- 响应式设计原则: 设计时从小屏起步、再逐级增强，布局以弹性为主、别把宽度写死，间距和字号用 rem、vw 这类相对单位打底，需要随视口连续变化的值用带上下限的 clamp()，断点只留给列数、导航这类结构级切换，复用组件按自身容器的宽度用容器查询适配。
- 界面只保留帮助用户理解、选择和操作的信息，避免重复表达。
- 拒绝通过叠加选择器权重或使用 !important 来强行覆盖样式；
- 完成任务后需要告诉用户怎么验收结果.
